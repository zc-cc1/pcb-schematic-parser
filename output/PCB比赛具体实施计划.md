# PCB 原理图自动解析比赛：具体实施计划

计划日期：2026-10-10。依据此前生成的《PCB比赛分阶段提示词》和用户提供的赛题 0803Rev1。

这是一份开发执行计划。本轮完成了提示词读取、赛事日期核验和候选仓库部分源码检查；尚未把候选项目在比赛数据上运行，以下质量、工时及参数都是待基线验证的计划值。

## 1. 目标、时间和范围

交付目标：输入一张 PNG 原理图，输出符合赛事格式的 components、pins、nets JSON；提供可运行代码/执行文件及 Word 技术报告。

官网当前显示报名截止 2026-10-16、作品提交截止 2026-11-07，见[官方赛程](https://cpipc.acge.org.cn/cw/hp/2c9080158ee9c272018f229208b610a6)。官网页面没有在赛程表中给出截止时刻，因此把 11 月 5 日设为内部首次完整提交日，11 月 6 日用于复核，11 月 7 日只留作应急。已报名的队伍跳过报名事项。

暂按单人每天 4–6 小时、约 145 小时开发工作编排；训练等待和长时间批量评测另计墙钟时间。GPU、每天实际投入和正式测试环境待确认。基线默认支持 CPU；GPU 主要用于可选微调和推理加速。

本轮主线：检测与 OCR 接入 → 元件文字绑定 → 引脚恢复 → 导线提取 → 电气网络构建 → 正式导出 → 按官方指标迭代。把提交入口、日志、坐标和评测器放在前几天完成。

首版不安排界面开发、整图生成编辑器、全新大模型训练或大规模数据贡献。SAM、检测微调、分割模型、多模态纠错和数据附加分作为有证据、有时间后再进入的工作项。

## 2. 开源代码怎么选、具体改哪里

优先审计 [HR-DONK/circuit-recognition](https://github.com/HR-DONK/circuit-recognition)，候选定位为检测/OCR 接口底座。仓库说明提供相应模块和模型；模型目录能看到权重文件名，但仍需下载和真实推理才能确认可用。

源码检查已经发现以下差距，见 [topology.py](https://raw.githubusercontent.com/HR-DONK/circuit-recognition/main/src/pipeline/topology.py)：

- `TERMINAL_POSITIONS['ic']` 为空；当前 `_get_terminals()` 只读取固定模板，没有在该函数中从 OCR 恢复 IC 引脚。
- 引脚引用使用器件标签和 left/right 等端点名，尚未达到比赛所需的 pin number、pinname 与连接坐标契约。
- 导线匹配无结果时调用 `_proximity_connections()`，根据器件邻近或对齐关系生成连接，缺少实际电气证据。
- 网络标签逻辑含正则过滤与转大写，无法直接保证覆盖任意信号标签，也不能直接保留严格文本口径。
- 每对端点建立 net 的方式和比赛需要的完整 pin set、逐 net edges 仍需适配及重构。

这些是已检查代码的事实；候选项目在本赛题中的实际 F1 尚未测量。

| 部分 | 首选处理 | 新增/修改位置（计划） | 首轮完成标准 |
|---|---|---|---|
| 检测模型接口 | 复用候选接口，检查权重类别和真实输出 | `adapters/detector.py` | 原图和切片均能返回类别、框、置信度及变换信息 |
| OCR 接口 | 首选候选 RapidOCR 后端；失效则接入独立后端 | `adapters/ocr.py` | 保留文本原文、框和置信度，能批量处理局部区域 |
| 文字过滤 | 保留可配置过滤，分别处理位号和 pin 小字 | `text_binding.py` | 不因统一尺寸阈值删除需要评分的小字 |
| 元件和文字绑定 | 实现方向、距离、类别和唯一性约束 | `components.py` | 输出稳定位号、type、Name、value 和 bbox |
| 引脚 | 实现独立模块，参考官方元件库及图像局部证据 | `pins.py`、`symbol_library.py` | 支持多引脚 IC、连接器、旋转和直接接触 |
| 导线 | 以 OpenCV 颜色/几何方案起步，Hough 作为候选证据 | `wires.py`、`junctions.py` | 不把文字和器件框直接纳入电气连通图 |
| 电气网络 | 实现图连通和同名标签合并；邻近关系只作待核候选 | `nets.py` | 生成完整 pin set，并把几何线段归属到正确 net |
| 官方 JSON | 实现统一转换和校验 | `exporter.py`、`validator.py` | 字段、大小写、引用、坐标和两点 edges 合法 |
| 平台运行 | 实现单图/批量命令，复用底层模块 | `cli.py`、`runtime.py` | 可计时、限次重试、及时保存输出，符合正式入口要求 |

候选依赖目前主要使用版本下限，见 [requirements.txt](https://raw.githubusercontent.com/HR-DONK/circuit-recognition/main/requirements.txt)。复现后锁定经过验证的具体版本，并与赛事环境对齐；不能直接把“安装最新版”视为兼容保证。代码、权重、训练数据和主要依赖的许可证分别记录。

备用方案：如果候选底座在一天内无法跑通最小例，切换到独立检测/OCR 适配器，继续使用同一套比赛模块。导线和交点可参考 [CircuitSchematicImageInterpreter](https://github.com/C-R-Kelly/CircuitSchematicImageInterpreter)，不在多个完整项目之间反复换底座。

[PCBnet](https://github.com/ECNUACRush/PCBnet) 当前说明未公开源码，用于数据和方法参考；公开数据与正式赛事 Golden 的字段、样本身份及许可证需要分别检查。

## 3. 总体实现结构

计划项目根目录：`C:/Users/Pc/Desktop/vision/pcb_parser_competition`。本轮不创建或声称已有这些实现文件。

```text
PNG
 ├─ 图像检查、切片及坐标变换
 ├─ 元件检测 ─┐
 ├─ OCR ──────┼─ 元件/文字绑定 ─ 引脚编号、名称、tip
 └─ 颜色/几何导线提取 ─ 交点和折点
                         ↓
              物理连接图 + 同名标签逻辑连接
                         ↓
              pin set、线段归属、特殊点状 edges
                         ↓
              官方坐标转换、JSON 导出和校验
                         ↓
              官方评测、错误可视化、实验报告
```

内部统一使用“原始图像、左上角原点、x 向右 y 向下”的像素坐标，方便 OpenCV/OCR 处理；切片结果立即映射回原图。仅在正式导出时转换为官方左下角坐标。用 Golden 校准像素中心/边界与 H 或 H-1 约定，防止翻转两次。

### 中间接口

| 数据 | 必须包含 | 输入验收 |
|---|---|---|
| 图像上下文 | case_id、原图宽高、颜色信息、切片和变换 | 宽高完整，所有变换可逆 |
| 元件 | 内部 uid、位号候选、type、OCR 关联、原图 bbox | uid 唯一；位号候选与原文有来源 |
| 文本 | text 原文、bbox、置信度、区域来源、候选用途 | 不覆盖原文；保留低置信度待核项 |
| 引脚 | component_uid、number、pinname、tip、证据和置信度 | 元件引用存在；编号冲突可诊断 |
| 导线 | segment_id、两个端点、像素证据、交点/折点关系 | 两端点格式正确；不是未经核验的虚构线 |
| 网络 | net_id、引脚引用集合、segment_id 集合、连接依据 | 所有引用可解析；物理/标签合并有记录 |

所有中间结果带版本、输入哈希、配置/权重版本与坐标声明。正式 JSON 不附加内部置信度等未获允许的字段。器件 body 框、官方 bbox 和 pin tip 分别保存，不强制认为引脚一定在官方 bbox 内。

## 5. 各关键模块如何实施

### 元件和 OCR：10/15–18

1. 扫描 Golden 的实际 type 分布，生成类别表。检测器的 ground、voltage_source 等输出不能只改名就视为赛题中的 gnd、vcc 或信号标签，需结合符号和文本区分。
2. 先跑原图，再对密集小元件和小字采用切片/局部放大；使用实际像素坐标回映射。
3. 为每个元件建立候选文本：位号、型号、值与引脚文本分开排序。
4. 用“距离 + 方位 + 字符用途 + 局部唯一性”选择绑定；局部冲突时扩大上下文后重识别。
5. 区分检测定位错误和位号/文本绑定错误，优先修复位号，因为它会传播到 pins 和 nets。

可先尝试的参数：切片边长 1024 px、重叠 128 px、检测置信度 0.25、NMS IoU 0.50；它们是实验起点，框定义和去重方法需按实际模型返回值核实。

### 引脚：10/19–22，主要工作量

1. 每个元件生成带四周上下文的局部区域，保留 body 框和引脚外端候选。
2. 彩色图利用颜色和短线形状找引脚，灰度图使用线段、方向和元件边界证据；仅把图中实际证据作为定位依据。
3. 在器件各边建立引脚序列，匹配附近的 pin number 与 pinname；不能把“第几个看到的引脚”直接当物理编号。
4. 通过官方元件库的符号、方向和镜像关系约束候选；核验库中的引脚号与图像使用的符号一致性。
5. 对多编号引脚按官方转换规则拆分；对未标号引脚核验自动编号与 pinname 规则。
6. 输出 tip 及其可视化证据；pin-wire 接触和 pin-pin 直接重合分别处理。

每天至少保留：一个困难 IC、一个连接器、一个无源器件及对应失败局部。模块诊断用真实元件作为输入；端到端验收用预测元件，分别记录，不能混报。

### 导线和网络：10/23–28

1. 彩色图先提取 wire 色彩候选；灰度图用几何候选及器件/文字区域约束。
2. 骨架或细线表示中识别端点、折点、T 分支、连接点及无连接交叉；断线修复只在有邻域方向和路径证据时做。
3. 构建物理连接图：节点为端点、连接点和 pin；边有实际线段证据。按已核验接触规则建立连通分量。
4. 按官方规则加入同名标签的逻辑连接；标签自身引脚和相接器件引脚均纳入 pin set。
5. 建立 segment 到 net 的归属；参考 Golden 的分段方式，不任意合并所有共线片段，也不为每个骨架像素生成 edge。
6. 处理零长度线段、飞线以及 pin 直接相接。标签间没有画线时不生成跨图长线。
7. 导出时生成 `pin_<number>` 和 `(component.number,...)`，转换坐标并检查引用。

8 类几何用例：直线、折线、T 分支、带连接点交叉、无连接交叉、局部断线、pin 直接相接、器件/文字干扰。

### 局部多模态纠错：10/29–11/02，可选

只对有具体冲突的区域触发：位号候选冲突、IC 名称不确定、引脚编号/名称矛盾或关键交点歧义。输入包含局部图、邻域上下文、原始 OCR 候选和结构约束，输出字段级修补；不默认重写整张电路。

修补通过结构校验和规则核验后才应用；保存修补前后值、调用耗时、Token 和失败记录。触发门限在开发集上比较收益，不凭模型自报置信度决定。

检测微调只在数据可用、许可明确、标注稳定且具备计算资源时进入。建议限定一次可控实验；是否保留由四项官方指标的实际变化决定。线段分割训练仅在颜色/几何方案的上限已被错误分析证实后考虑。

## 6. 数据和评测安排

### 数据集合

- 快速调试集合：从开发集中选 6 例，建议 2 中等 + 4 困难，覆盖 IC、密集小字、重复标签和复杂连接。用于每次修改的即时检查。
- 固定开发集：数据足够时至少 20 例，建议 8 中等 + 12 困难；用于算法选型和参数比较。
- 最终保留集：条件允许时保留 10 个独立源工程案例，建议 4 中等 + 6 困难；不参与日常调参。
- 训练集：使用其余获准用于训练且标注合法的案例，或额外合法收集的数据。不同导出版本、切片和增强图按源工程分组。

这些数量是数据充足时的建议。如果正式数据不足，先按实际来源分组，报告样本不足和覆盖缺口，不能靠复制图片扩大有效样本数。

缺官方评测器时，先实现明确标记为 proxy 的评测入口，保存匹配差异；不要用图像分割 IoU、OCR 字符准确率或普通检测 mAP 代替官方四项 F1。缺真实 Golden 时，可为小规模公开图建立人工复核标注以验证接口，明确其来源及局限。

### 必须记录的指标

| 类别 | 指标 |
|---|---|
| 比赛质量 | 每例 ComponentF1、PinF1、NetHypergraphF1、NetLineF1 和四项加权分 |
| 数据分组 | 中等/困难的实际例数与平均分；全预测和固定真实上游的诊断分别记录 |
| 工程正确性 | Schema 合格率、无效引用数、重复 key、坐标越界、坐标往返误差 |
| 运行情况 | 全部指定案例数、完成/失败/超时数、各阶段耗时、冷启动总耗时、单例 P50/P95 |
| 模型成本 | 权重/配置版本、调用次数、实际 input/output/total Token、重试和调用失败 |

全案例加权分的分母包含全部指定案例，失败和未完成例不能从报告中剔除。Token 记录用于比较成本；比赛 Token 分按队伍排名赋分，本地不能仅根据消耗量计算。

首轮建议质量目标：C=0.80、P=0.70、H=0.65、L=0.60，对应四项加权分 70.25。后续目标可设 C=0.90、P=0.85、H=0.80、L=0.80，对应 84.25。两者均不是已有成绩或官方晋级标准，10/13 测完基线后需要修订。

### 实验顺序

| 实验 | 只改变的主要因素 | 要回答的问题 |
|---|---|---|
| E00 | 原始检测/OCR + 最小正式输出适配 | 原始底座实际缺什么、失分多少？ |
| E01 | 切片及坐标回映射 | 密集目标是否提高，接缝重复是否恶化？ |
| E02 | 文字绑定规则 | 位号和 Name/value 是否减少串配？ |
| E03 | 独立引脚模块 | 编号、名称及 tip 定位分别改善多少？ |
| E04 | 物理图与同名标签合并 | 错并网/漏并网是否减少，线段归属是否正确？ |
| E05 | 局部模型纠错或可选微调 | 在运行预算内，净加权分收益是否值得？ |

前置改造可能需要多个小实验。表中编号代表主要版本对照，不能把不相关修改混成一次实验后宣称每项都有效。

判断收益时，使用 `ΔS=100×(0.30ΔC+0.25ΔP+0.35ΔH+0.10ΔL)`；同时查看各困难案例退化情况和完整运行成本。每轮先测 6 例快速集，通过后再跑固定开发集。只有新的改动、失败或未解决问题才追加验证。

## 8. 时间、资源及降级规则

### 推理预算

用 50 例做预算：官方两小时折算为平均 144 秒/例，包含全部开销；内部 100 分钟目标折算为平均 120 秒/例。先把基础流水线的平均单例目标设为 90 秒以内，为加载、长尾和纠错保留时间；实际按冷启动整批测量验收，不能只测模型 forward。

第一版就实现有限重试与逐例日志。重试建议不超过 2 次，计入总耗时和 Token。按剩余时间预算限制额外纠错。若平台支持统一批量调度，可先为全部案例生成基础结果再选择纠错；若平台逐图调用，则每例限制纠错预算。

| 条件/问题 | 处理决定 |
|---|---|
| 没有 GPU | 完成 CPU 推理、OCR、CV 和平台允许的局部 API 路线；GPU 训练保持可选 |
| 候选底座一天无法复现 | 保留审计结论，切独立检测/OCR 适配器，不阻塞引脚和网络实现 |
| 官方元件库/Golden/评测器缺失 | 分别登记缺失；完成确定接口及人工小例验证；报告暂无法验证的正式规则 |
| 重复标签编号无法从 PNG 唯一恢复 | 对齐官方转换器和公开 Golden，向赛事渠道核实；不得假称扫描顺序等价 |
| 10/22 引脚目标未达 | 优先困难 IC 的编号、tip 和元件 key；根据错误分布压缩可选模型训练 |
| 10/28 尚未跑通完整 JSON | 暂停新增算法，修复引用、坐标、网络与导出链；保留已能运行的基础版本 |
| 11/02 质量目标未达 | 按固定开发集选最好的已验证版本冻结；如实报告质量，不以未达到建议值推迟打包 |
| API 出错/限流 | 有限重试，保留基础输出和失败日志；把不可用纠错从可选路径关闭 |
| 批量超过 100 分钟 | 优先减少额外纠错、重复 OCR 和无效重试；在相同案例上复核质量变化 |

GPU 具备时，以实际显存和小批次试运行设置训练/推理 batch，不凭显存数字承诺可训练规模。正式 Python/PyTorch、硬件、联网权限、模型 API、usage 计量和入口必须在阶段 0–2 核验；超出官方支持的框架组合按要求准备可运行 Docker，并核实容器中的 API 访问。

## 10. 人力较少或每日时间较短时怎么调整

如果每天只有 2–3 小时，把约 145 小时计划压缩为约 70–85 小时：保留规格、评测、坐标、元件文字、引脚、网络、导出和提交；将开源复现限定在一个主要候选加一个备用；取消额外界面、大规模收集、分割训练和多次微调。局部 API 纠错只在已经跑通且有净收益时保留。质量目标按基线调整，截止日期和格式验收不变。

多人协作时，可分别负责检测/OCR与坐标、引脚/导线、网络/评测/提交，但先冻结接口、数据划分和正式输出契约；由一人维护主分支及最终全预测评测。这个分工是人力建议，本轮未创建代理任务或启动实现。
