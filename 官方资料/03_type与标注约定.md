# 标注约定：type、Name、坐标系、bbox

> 这一份处理的是“**格式对了但字段含义对不上**”的那类丢分。四份资料之间自相矛盾的地方都在这里。

| 资料 | 类型数 | 实测取值（按频次） |
|---|---:|---|
| `赛题Q&A1013.docx` 提到的 `type_list` | 官方称 **34** | **文件未发布** |
| `10_GTcase`（10 例，官方 golden） | 20 | `r` `gnd` `c` `net_input` `box` `v` `l` `mosfet_npn` `pin` `d` `net_output` `other` `battary` `crystal_2pin` `switch` `bjt_npn` `led` `bjt_pnp` `amp` `circle_header` |
| `open_GT`（13 例，新口径） | 11 | `gnd` `c` `r` `v` `box` `led` `l` `net_bidirection` `d` `switch` `pin` |
| `200_train_cases` | 41 | 上面 20 类 + `amp_3pin` `amp_5pin` `ant` `bjt` `block` `buzzer` `crystal` `crystal_3pin` `crystal_4pin` `dc` `esd` `fuse` `jumper` `m3螺丝` `mosfet` `mosfet_pnp` `motor` `net_short` `opt` `seg` `testpoint` `transfomer` |
| `case_001_扩展示例.json`（官方示例） | 4 | **`vbus_in` `resistor` `ic` `gnd`** ← 长名，与短枚举互斥 |
| 赛题 PDF 正文 | — | 用 `ic` / `resistor` / `capacitor` 三词（p7），附录又说“boxic/box … 对应 type 字段为 `ic`”（p11） |

**三份数据共有的 type 只有 10 个**：`box` `c` `d` `gnd` `l` `led` `pin` `r` `switch` `v`。

**已确认可用子集**：`open_GT ∪ 10_GTcase` = **21 类**（两份官方 golden 的交集）。
四份并集 = **43 类**，超过官方声称的 34 类 → 说明训练集里确实有 `type_list` 之外的历史写法。

**要做的**：
1. 输出前过一张归一化表（至少 `ic→box`、`resistor→r`、`capacitor→c`、`buzzer→buzzer`…），并保留原始写法做诊断；
2. 用 `_derive/type_candidates.json` 里的 `union_gt_only` 当白名单做自检（不在其中的 type 一律告警）；
3. **向官方索取 `type_list`**——这是目前唯一还缺的官方文件。

## 2. `Name`：位号还是型号？

| 资料 | 事实 | 含义 |
|---|---|---|
| `10_GTcase` | **184/184 个元件 `Name == key`**（都是 `U1`、`R5` 这种位号） | 这是**旧口径** |
| `open_GT` | 346 个元件里 **41 个 `Name != key`**，且这 41 个全是 box/ic 的**芯片型号**（`"U1": {"Name": "IP5306-4.35V"}`） | 这是**新口径** |
| Q&A 一般 #10 | “key 填 U1 U2，name 是芯片名字” | 明确要求新口径 |
| PDF p7 / p17 注 c | `ic`（=box）的文本比较的是 `Name` | Name 进分 |

⇒ 在旧 10GT 上做“ic 比较 Name”的本地评分，**正确预测（Name=型号）会被判错**。
⇒ 判别“这个元件能不能拿去查库”的条件是 `Name != key`，不是“Name 在不在库里”（库里有真名 `U1` 的元件，会假命中）。
⇒ 回归集应该换成 `open_GT`（13 例 / 346 元件 / 692 引脚 / 231 网络）。

## 3. 坐标系：左下原点、y 向上（已实测）

官方三处说法：

| 出处 | 说法 |
|---|---|
| `README.md`（数据集说明） | “坐标均对应各 case 的原始 PNG 图像坐标系”（暗示左上原点、y 向下） |
| PDF p11 / p26 | “沿用原始 ParsedJson 的**左下角坐标系**：x 向右增大，**y 向上增大**”；bbox 的 `(x1,y1)` 是左下角 |
| Q&A 一般 #11 | “赛题 / 评测 / golden 测试案例 / 自行收集数据集**均为左下角为原点，X 向右，Y 向上**”，并注明“数据收集指南文档已修改，将坐标系统一” |

实测（用墨迹做判据）证明 Q&A/PDF 对、README 错：

| 测试 | 直接取坐标 | `y → H−y` 翻转 |
|---|---:|---:|
| 0025 的 18 个引脚点落在墨迹上 | 5 / 18 | **17 / 18** |
| 0100 的元件框内墨迹密度 | 0.116 | **0.247** |

⇒ 提交必须是 **y 向上**；管道内部已经做了 `H−y`，**不要再翻转第二次**。
⇒ 回归测试建议：拿 0025 跑“引脚点墨迹命中率 ≥ 90%”，一条命令就能抓出坐标系回退。

## 4. `bbox`：是本体框，不是含引线框（新证据）

PDF p26：每个元件有**外侧框（outer bbox）**与**内侧框（body bbox）**，**引脚 tip 在外侧框边缘，base 连到内侧框**。
但 `components.bbox` 到底填哪个，官方没写死（Q&A 一般 #23/#24/#27/#28 都在问，回答一律“以即将更新的 10GT 为准”）。

**用数据判定**：GT 的引脚点相对 GT 的 bbox 在哪里？

| 资料 | box 元件 | 引脚点 | 落在 bbox 边上（±3 px） | 落在 bbox 内部 | 落在 bbox 外部 |
|---|---:|---:|---:|---:|---:|
| `open_GT` | 31 | 191 | **0** | **0** | **191（100%）** |
| `10_GTcase` | 15 | 101 | 6 | 0 | 95（94%） |

⇒ **GT 的 `components.bbox` 是本体框（body），所有引脚点都在框外**。
引脚到框边的距离（每个元件取中位数）：`min 3` / **中位 20** / `p75 20` / `max 40`，
其中 **10/45 个元件 > 20 px**（`TPS61240DRVR` 40、`MT2492` 40、`TYPE-C 6P(073)` 39、`RT7272BGSP` 29、`SY6912AFCC` 26 …）。

这解释了两件事：

1. **本地 IoU≥0.5 的匹配门把元件全判掉了**：0025 的预测框与 GT 框 IoU 只有 **0.09**（中心偏差 <1 px，但框大了约一个引线长度）。
   → `component_matches = 0` → pin / net 全 0 → box 库 A/B 的 on/off 完全一样（0.1738 = 0.1738）。
   → **本地分数系统性偏低，不能用来判断“库有没有用”。**
2. **提交含引线的框会真实丢分**：官方 bbox 容差 20 px，而引线长度中位数正好 20 px、最大 40 px。
   若容差按边/坐标差计算，那 10/45 的 box 元件会因为框多了引线而直接判错——**这是纯格式问题，零成本可修**。

⇒ 提交前要把检测框收缩到本体框（或按 `bbox` 外扩引线长度的方式反推），但对 `r`/`c` 这类两脚器件，
本体框就是器件矩形本身，不需要收缩。

## 5. 引脚编号的两条官方规则（还没实现）

| 规则 | 原文 | 现状 |
|---|---|---|
| pinNumber 为空 / `∅` / OCR 噪声 → 自动编号 `pin_1、pin_2…` | PDF p17、p18 注 c | 已实现（R15） |
| **一个引脚多编号（如 `"5,6,7,8,9"`）拆成 `pin_5、pin_6…` 多条独立条目** | PDF p18 注 d | **未实现** |

第二条对 GND/VCC 尤其重要：GT 里同一个电源符号会以多个编号出现（如 `∅28.23`），
而我们的导出只写一个键，hyperGraph 的 pin set 自然对不上。
